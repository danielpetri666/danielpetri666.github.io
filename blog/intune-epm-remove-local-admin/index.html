Intune EPM: Remove Local Admin Without Breaking That One App

Use Intune Endpoint Privilege Management to give one support task the rights it needs.

The Problem

The user needs to run one maintenance utility. The support ticket ends with their account in local Administrators. The utility gets its five minutes. The account keeps the rights.

Endpoint Privilege Management (EPM) changes the unit of approval to the file and the conditions under which it can elevate. Microsoft’s deployment guidance starts with reporting, then uses the observed elevation activity to build rules. That order matters. An elevation event is a lead. Find out who owns the app and why it needs those rights before turning the event into a rule. Deploy Endpoint Privilege Management

Licensing

Endpoint Privilege Management has been included in Microsoft 365 E5 since July 1, 2026. Microsoft 365 E7 also includes EPM. If you already have E5, the July change gives you a reason to revisit the local admin exceptions your team still maintains. Start with one utility and an elevation rule you can verify. Implementation

The rights model

I’d map the request to three things before touching Intune: the user who needs to do the work, the file that performs the operation, and the operation Windows will allow once it runs elevated.

That last part is the one I care about. An elevation rule can match the right file and still be a bad rule. A utility that opens a service console has a different risk profile from a utility that can start arbitrary programs. A signed maintenance bundle may contain both. The signature tells you who signed it. You still have to decide which of their binaries gets the exception.

Start with EPM reporting on a scoped group. The report helps answer which elevations are happening and which process is involved. I would still ask the application owner to name the task. “This process ran elevated last week” is a weak reason to approve it next week. Pair the report with the actual support workflow. Which button needs the rights? What happens if the user skips it? Does the task need elevation at all on the current version?

The Windows elevation settings policy and the elevation rules policy do different jobs. The settings policy turns on the EPM client and establishes such things as the default response and reporting. The rules policy describes how to handle a matched file. Write down both for the pilot. With Deny all requests, EPM denies explicit elevation requests for files that match no rule. A matching rule gives Build A its exception. Build B hits the default.

Build a rule somebody else can review

A hash is a good fit for one known version. Read it from the exact file you intend to permit, keep the filename and any other required rule attributes visible, and give the rule a useful name. “Temporary admin” describes nothing. “Run the lab label-printer maintenance utility, approved build” gives someone a starting point.

I would require the request to include the vendor, version, why the user cannot do the task as standard user, and what will trigger a re-review. The person who owns the utility should know they have to bring the next version back. That is part of the cost of pinning the file.

Publisher-based rules change that calculation. They can reduce the work when a vendor ships regularly, but you have to account for every file that can match the resulting rule. I’d consider the signer alongside narrowed file attributes and the trustworthiness of the deployment location. Start broad and you get to spend the next incident working out how broad it actually was.

Choose the elevation experience

There is a support decision hiding in the rule configuration. A routine action that you have already reviewed is different from a new request that needs someone from the team to look at it. Microsoft documents automatic, user-confirmed and support-approved elevation paths. I would start with explicit user confirmation for a known file and compare that with the workflow my service desk can actually support. A ticket queue that nobody monitors can turn a sensible approval design into an outage. EPM elevation rule types

The child process choice belongs in that review as well. If the utility launches a separate maintenance binary, decide whether the child should run at the elevated level, require its own rule or run without the parent’s elevation, using the behavior Microsoft supports for the chosen configuration. Verify it with a benign dependency. A clean result for the original EXE by itself says very little about the rest of the task.

Configure the two policies

I verified the rule on an Intune-enrolled Windows 11 VM in Hyper-V, using a standard user and a dedicated device group. For your own pilot, use a supported Windows endpoint. Microsoft lists Azure Virtual Desktop single-session and Windows 365 as supported virtual platforms. Use a separate lab administrator to place the files in the protected folder. EPM prerequisites

I compiled the same small C# program twice as x64, with the output named EpmLabMarker.exe both times. The default build writes Build-A to a dedicated HKLM value. Defining BUILD_B when compiling the second build changes the marker to Build-B and gives the executable a different SHA-256 hash.

In Endpoint security → Endpoint Privilege Management → Policies, use the two Windows policies below. Assign the settings policy to the group containing only the lab VM. Wait for it to apply and capture the baseline before assigning the rules policy to that group.

Run the same test with both builds

  1. As a separate lab administrator, place Build A in the protected folder and calculate its SHA-256 with Get-FileHash -Algorithm SHA256. Use that hash in the rule. Before the baseline, verify that the dedicated lab marker is absent. If it is left over from a previous run, clear only that test value as the lab administrator and verify that it is gone.

  2. As the standard user, run A normally to establish the baseline. Once the settings policy has applied, use Run with elevated access and capture the denial before assigning the rules policy.

  3. Assign the rules policy to the lab group. After it applies, run A again using Run with elevated access and select Continue. Read the registry value from an ordinary PowerShell window:

    reg.exe query 'HKLM\SOFTWARE\EpmBlogLab' /v Marker /reg:64

  4. As the lab administrator, replace A with B at the same path. Verify the installed file has B’s hash. Leave the rule and the Build A marker in place. Request elevation as the same standard user, then read the marker again.

Read the results in the right order

If the approved file fails, check policy delivery and effective settings before making the rule more permissive. Confirm the test account really is in scope. Confirm you ran the intended executable, from the intended location, and whether the operation actually got far enough to touch the admin-only resource. An app can open its window as a standard user and fail only when it commits the change.

If both builds elevate, stop the pilot. Check for residual membership in local Administrators, other matching rules and defaults that can allow elevation. A successful elevation result in the EPM report shows that elevation succeeded. Verify the operation separately on the client and check that nothing else in the workflow gained permissions you did not intend.

The regression test belongs in the next version change. Run the newly approved build and a build that should remain outside the rule. If the support process cannot afford that check, reconsider the design. An exception with no owner and no test is how the old local-admin problem comes back with a nicer name.

Known Limitations

A hash-pinned rule needs to be reviewed when the executable changes. Intune processes EPM report data once every 24 hours. I used the client readback for the test result. The Managed elevations report can provide additional evidence for the approved run. The test tool did not launch child processes. EPM reports

Security Considerations

Treat each rule as a privilege grant. Review the file attributes and child process behavior together, verify the pilot user’s local group membership, and keep an owner for each exception.
